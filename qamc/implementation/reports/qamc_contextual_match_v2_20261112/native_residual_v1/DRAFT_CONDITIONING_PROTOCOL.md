# PersistBench draft-conditioned admission development protocol

This protocol freezes the source roster before any candidate generation or scoring. It uses 12 exposed roots from the earlier author-control cohort. All have saved full and no-memory endpoint scores, and none share the original cohort's source-group ID with the 14-root switch panel. There are 6 strict beneficial-use opportunities (full passed, no-memory failed), 2 misuse opportunities (full failed, no-memory passed), and 4 cases whose two archived endpoints passed. The archive had only two eligible misuse groups after source exclusion. This is an outcome-stratified development panel, with historical endpoints used for sampling and reporting only. The sealed cohort is outside this protocol.

## Mechanism and controls

1. Render a true task-only draft with the pinned PB_RUBRIC generator and empty history. Share that draft across all arms except the control that deliberately hides it from the selector. No scorer is called until final answers exist.
2. Use one read-side call per arm. The proposed selector identifies a concrete useful change to the actual draft, cites the minimal jointly sufficient original sources, and returns original IDs. Admit a source for a supported current fact, applicable constraint, or a legitimate soft preference with a concrete purpose. An already satisfied need, a private preference that would change someone else's decision, and an unsupported premise in the draft do not license extra evidence. The executable result is a subset of original IDs in original order. Exact grounding can be tested mechanically; semantic validity still depends on the selection model.
3. Compare three controls. Give the same selector Query and history but hide the draft to isolate the additional information. Give a strong ordinary selector the same visible draft and history and let it directly pick useful IDs without a witness contract. Give a free preparation control the same task-only draft and full history, then let the final Actor freely use its preparation and full history.
4. Generate fresh final answers with one PB_RUBRIC Actor call per arm. The first three paths use the same Actor template and see only their compiled originals, with no selector prose or draft forwarded. In particular, an empty selection still gets one fresh final draw. Compare with the archived stronger endpoints separately. Reuse any identical request only with an explicit shared outcome and keep its inference-time logical cost distinct from new physical calls.
5. Compare the same projects' fixed GPT-4.1 rubric scores on common valid items, per-track pass/fail, positive and negative changes, score disagreement, and actual behavior. Failed calls and invalid witness structures are missing. Report coverage failures and source selections before reviewing final scores. Missing receipts must not be scored as abstention.

If every logical cell needs dispatch, the cap is 12 shared draft calls, 48 preparation calls, 48 final answers and 48 scores, for at most 156 physical requests. Historic comparisons and eligibility checking are zero-call. The new comparison must improve over both the ordinary draft-aware selector and the no-draft witness selector with credible behavior on at least two distinct roots. At least one credible benefit must use a nonempty selection. Preserve supported utility and avoid new unsupported facts, material task omissions or misuse. A failed finite screen closes this mechanism variant. This is a development screen and provides no SOTA evidence. A later confirmation would require separate authorization and a matched native protocol.

## Revised first experiment after external critique

The panel above remains frozen. Before any dispatch, the selector comparison and its 156-request budget were superseded. Earlier draft-aware editing already supplied substantial contrary evidence. This experiment now tests only the final exposure to an original draft, not draft-aware source admission.

All arms share a new no-history PB_RUBRIC draft and one concrete-action proposal produced using that draft and the original history. Both final Actors receive the same original history, same proposal, same task, same PB_RUBRIC system strategy and same final instruction. REVISE additionally receives the draft. RESOLVE does not. Both generate a fresh full answer, including when the shared proposal abstains. IDs are validated before dispatch; their usefulness and whether an erroneous action was truly replaced require behavioral inspection. No source label or old score enters the inference requests. The ceiling is 72 physical calls, including scores. Report the two arms using all common valid items with missing cells preserved, preserve archived PB_RUBRIC as the performance reference, and require at least two roots with defensible behavior and an improvement over matched REVISE without damage to useful memory or task completeness. Archive methods differ in request and timing. No confirmation or published ranking follows.
