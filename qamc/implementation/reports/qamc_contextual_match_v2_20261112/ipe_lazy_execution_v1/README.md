# Lazy IPE-C generation cost on the exposed RPEval panel

Predict the IPE ranking for every visible candidate in one call. If any top rank is C, obtain the MLE ranking in one additional call and pass both estimates to the original RP aggregation and Actor. Otherwise call the original task-only Actor immediately. The program adapter accepts the existing request/validation callbacks. read_orders must verify candidate coverage and IDs before exposing the ordered strategies. An invalid estimate remains an error. This implementation applies to the nonempty candidate protocol tested here.

We recovered the switch for 295 of 300 development tasks from the individual IPE rankings, matched it to the frozen branch, and checked available answer hashes against that branch. Five routes are unknown. On the 274 tasks where all three endpoints have a Match score, history is enabled 125 times and disabled 149 times. Cold nominal generation cost is 673 requests versus 822 for full RP (149 fewer, 18.1%). On this same intersection their archived Match totals are 953 and 824 out of 1462. Always empty scores 874 and takes 274 nominal calls. Across all 295 identifiable routes, 727 calls are needed versus 885.

These counts describe successful logical execution from scratch, excluding grading, retries, and shared caches. This read-only replay used zero new model calls. It supplies neither observed token savings nor a wall-clock speedup. The enabled branch executes two estimators sequentially; full RP can run them concurrently. Five unknown routes cannot be assumed free. The exposed-panel results do not establish independent efficacy. See the original formal runner's initial_bodies and RP generator construction, and ipe_c_two_endpoint_completion_v1/RESULTS.json in the restored research checkout.

### Receipt-based resource comparison

Two earlier fresh deployments on the same 18 development groups ran both estimators and both Actor endpoints for comparison. For each deployment, charge each method only the exact calls it needs. Across these deployments the lazy method uses 89 requests and 557,978 reported tokens, versus 108 requests and 781,190 tokens for full RP (28.6% fewer tokens). Task-only uses 36 requests and 35,159 tokens. Do not add these overlapping paths to estimate a bill. Every one of the 144 distinct source/deployment/generation-stage receipts had known usage, OK status and zero automatic retries. Judges are excluded. This resource comparison includes all 18 tasks twice; one second-deployment Match record is invalid for quality comparison. In deployment 1, IPE-C/full RP scored 38/91 vs 40/91; in deployment 2, 44/87 vs 40/87. No inference about independent performance follows from repeated use of the same groups.

Service durations yield a different tradeoff. Assuming full RP overlaps its estimators perfectly, each full-history task on the lazy path must instead wait for both in sequence. Among enabled tasks the respective lazy/full modeled median seconds were 207.91/127.81 in deployment 1 and 157.33/113.34 in deployment 2. Queueing, start offsets and service interactions are excluded. These are critical-path projections, not measured online latency.
