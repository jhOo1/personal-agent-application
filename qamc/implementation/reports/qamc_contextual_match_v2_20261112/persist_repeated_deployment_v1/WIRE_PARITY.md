# PersistBench generation contract parity

The frozen repeated-deployment study compares complete deployed methods. The SELECTED_GEPA renderer and the archived full-history GEPA baseline share the same GEPA text. A zero-call audit rebuilt the candidate Actor request as if all original memories had been selected, keeping every other candidate parameter. On all 25 roster tasks, the resulting messages and other request fields match full-history GEPA byte for byte except for the output cap. SELECTED_GEPA uses 8,192 tokens; PB_GEPA and PB_RUBRIC use 4,096. The cap difference originates in the original archived method contracts. The experiment preserves them as frozen.

By the end of wave two, one available SELECTED_GEPA answer on a cross-domain task had 4,377 reported completion tokens after subtracting reported reasoning tokens. This is a usage-derived estimate. That answer passed the project Judge, as did full-history GEPA on the task. The cap could affect generation or transport even for answers below 4,096 visible tokens. The head-to-head results are deployment comparisons. A strict mechanism attribution to evidence filtering would need the same cap and other generation settings.

The older PB_NO_MEMORY answer is useful context for interpreting bypass of historical bias, but none of the 25 old empty-history wires equals the empty-input SELECTED_GEPA request. The older empty-history baseline used a different prompt template. It cannot answer whether routing adds utility over an always-empty GEPA of the same configuration. The exact empty SELECTED_GEPA wire was actually allocated in six SYC and six CD cases in draw one, and five SYC and six CD in draw two. These are request allocations and include failed deliveries. No BU draw used an empty selection in either wave. A future explicit matched empty-history comparison can use exact valid receipts where appropriate, with the intended sampling unit defined in advance.
