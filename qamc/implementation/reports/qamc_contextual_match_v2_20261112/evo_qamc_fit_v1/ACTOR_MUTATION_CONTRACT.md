# What actually changes in the feedback-guided Actor comparison

One offline call saw scored development contrasts and proposed the two general instruction additions recorded in the linked contract. The accepted strings contain general policy language. The request auditor checks all 80 new Actor requests against the existing selected-history task-plan parent. Each repeats the same current task, facts, exact task plan, visible history, model, sampling settings and output budget. Only the corresponding general instruction is appended to the parent system prompt. The raw offline feedback appears only in the proposer request. That private request and the paired source traces are not distributed.

The scope instruction tests whether historically sourced facts and preferences remain subordinate to the authority granted by the current task. This is useful to evaluate in the group-lunch and child-exhibition examples. The realization instruction tests whether applicable preferences are actually reflected in the deliverable without losing facts, formal appropriateness or completeness. Its wording assumes applicability has already been determined, so it can also amplify a mistaken selection. The two directions may affect different benchmarks.

The baseline for each candidate is the identical inherited input without the added instruction. This is a single deployment per candidate on exposed tasks and uses the same frozen scoring adapters. Judge, actor inputs and source selection remain distinct. Passing the structural and copy checks does not establish generalization, privacy beyond the checked request boundary, or better end answers.
